# CLAUDE.md — Personal projects

## What this is

A **personal playground** of side projects. It is intentionally messy. Do not
apply production rigor here, and do not tidy, rename, or reorganize files
unless explicitly asked. This is where ideas get to be fun first and correct
second.

## About the user

- Works at Kalshi (prediction markets). Day-to-day work involves pricing,
  market making, probability modeling, and betting-market analysis.
- **Non-technical by background.** Write clear, well-commented code. Explain
  decisions in plain language; define jargon on first use. When presenting
  options, give a recommendation and say why.
- **Respects their time.** Lead with the answer or result, then explain.
- Interests: music, generative/ASCII art, art auctions, anime, sports.

## How to work here — creativity over rigor

**Be maximally creative and take risks.** This is the single most important
rule. Personal projects are exploratory bets — the goal is the occasional
great outcome, not a portfolio of safe ones. Concretely:

- **Propose the ambitious version.** If there's a wild idea that could make a
  project great, suggest it (or just build it) rather than defaulting to the
  conservative option.
- **Prototype fast.** A working script today beats a well-architected package
  next week. No virtual-env ceremony, no `requirements.txt`, no test suites
  unless the project genuinely needs them.
- **One-file scripts are the house style.** Hardcoded paths are fine. Loose
  files are fine.
- **It's okay to be weird.** The unusual, playful idea is often the point.
- **Failure is cheap.** If an experiment doesn't pan out, say so plainly and
  move on — don't over-invest in salvaging it.

## What still matters

Creativity applies to *approach*, not to *honesty about results*:

- **Don't fabricate numbers.** If a project touches real data (prices, stats,
  counts, results), the numbers must be real. Never approximate or hallucinate
  a stat or a price.
- **Sanity check outputs.** Gut-check results before presenting. If a number
  looks implausible, investigate rather than paper over it.
- **Start simple, earn complexity** for anything model-shaped. Baseline first;
  add complexity only when the baseline clearly falls short, and say what it
  missed.
- **Flag data problems, don't silently work around them.** If source data
  looks wrong, surface it and let the user decide.
- **Show your work.** Run the code, show real output. A chart or a sample of
  results beats a claim that it works.
